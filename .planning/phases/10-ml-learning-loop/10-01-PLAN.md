## Phase Goal

O analista carrega em «Treinar» na aba 📦 Models, vê o botão dizer «A treinar…», recebe uma frase que diz exactamente o que aconteceu à versão nova — incluindo que o backend ainda não a usa e que é preciso reiniciá-lo — e volta a ver a tabela com a nova versão. Sem polling, sem ficheiro novo, sem uma segunda superfície de API.

<objective>
Fechar a primeira metade do learning loop do ponto de vista do utilizador: **treinar a partir do dashboard** (D-01) com a UX honesta que o caso `loaded ≠ active` exige.

O caso que manda em todo o plano: um `POST /api/ml/train` que devolve 200 cria `models/vN/`, grava o `metadata.json` e aponta `ACTIVE` para ela — mas a cache do modelo é **por processo** (`ml_anomalies.loaded_version()`), portanto o backend continua a medir com a versão anterior até ser reiniciado. Um botão que devolve 200 e produz uma versão que o dashboard continua a não usar é a pior UX possível, e a resposta honesta não é esconder o treino: é dizer «a v3 foi criada e está ativa, mas o backend continua a usar a v2 — reinicia o backend». É esse o critério que separa este plano de um `fetch` e um `alert`.

O segundo caso que manda: **erro ≠ sem dados**. Um 409 (já há um treino a correr), um 422 (parâmetros fora dos limites) ou um 503 (registo indisponível) desenham-se como erro, com a mensagem traduzida do código — nunca como a linha vazia «Sem dados — ainda não há modelos registados», que significaria "não há modelos" quando o que há é uma falha.

`ml_models.js` fica com o botão porque D-07 põe o treino na aba que já mostra o registo: um ficheiro novo na raiz entraria na whitelist do `serve_frontend.py` (que este plano não pode tocar, e não precisa de ser tocado) e criaria uma segunda `MutationObserver`, um segundo ciclo de dados e um segundo par de listeners para o que é uma acção sobre o MESMO registo que a tabela da aba já mostra. Sem `setInterval`, sem `202`/`job_id`, sem estado de treino a consultar: um `IsolationForest` treinado sobre a janela do Indexer são ~3 s medidos (10-CONTEXT, D-07), e um `await` normal é a interface certa para três segundos.
</objective>

Contrato do backend assumido (a confirmar na Task 3 — `<precondition>`):
```
POST /api/ml/train   {"dataset": "latest_export"|"synthetic",
                      "dataset_origin": "real"|"synthetic"|"unknown",
                      "contamination": 0.01..0.5, "random_state": 0..2^32-1,
                      "n_estimators": 10..1000}
   -> 200 {"version": "v3", "active": "v3", "loaded": "v3"}
   -> 401 | 409 detail="training_in_progress" | 422 (detail = lista do FastAPI, não é string)
   -> 404 | 503 (detail = código de ERROR_CODES)
```
`422` é o caso a não esquecer: o `detail` do FastAPI é uma **lista de objectos**, nunca uma string, por isso `mlmCodeFromResponse` devolve `http_422` (a guarda `typeof detail === "string"` em ml_models.js:78 trata-o). É exactamente o que se quer: nada do pedido volta ao DOM.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/ml/train` | É a primeira rota do projecto que **escreve** em `models/` a partir do browser; quem tem a API key passa a ter escrita em disco (D-08). O corpo é o que o browser decide — daí `mlmTrainBody` reduzir a duas chaves de uma lista fechada |
| `/api/ml/train` → browser | A resposta só tem `version`/`active`/`loaded`; um erro traz um `detail` que pode ser texto de exceção, uma lista de validação ou HTML. Entra como CHAVE de lookup, nunca no DOM (API-02) |

| browser → `index.html` / `style.css` | Markup e CSS estáticos servidos pela whitelist; o JS é o único que escreve no DOM |
